# User identity

## Decisions

- 사용자는 이메일만 입력해 식별한다. 비밀번호는 요구하지 않는다. 같은 이메일로
  접속하면 같은 사용자로 취급하고, 그 사용자가 저장한 여행 목록을 그대로 보여준다.

## Boundaries

- 이 방식은 첫 스펙(`docs/specs/trip-weather/`)의 로그인·마이 여행 저장 기능에
  적용된다. 실사용(프로덕션) 단계로 넘어가기 전에는 재검토가 필요하다.
- 비밀번호·소셜 로그인·계정 복구는 이 결정의 범위 밖이다.

## Why

PRODUCT.md는 "로그인 계정으로 여러 기기에서 같은 여행 목록에 접근"하고 "사용자마다
여행 일정이 섞이지 않게 격리"되는 것을 요구한다. 정식 비밀번호 인증은 이 요구를
충족하는 데 필수는 아니며, 첫 스펙의 목표(핵심 흐름을 한 번에 구현하고 실제 동작으로
검증)에 비해 구현 비용이 크다. 이메일만으로 식별해도 다기기 접근과 사용자별 격리라는
두 요구는 그대로 충족된다.

## Reconsider when

- 실사용자에게 서비스를 열 계획이 생기는 시점: 타인의 이메일을 입력해 그 사람의
  여행 목록을 볼 수 있는 위험이 있으므로, 그 전에 반드시 정식 인증으로 전환해야
  한다.

## Still-rejected alternatives

- 비밀번호·소셜 로그인 — 첫 스펙 범위에 비해 구현 비용이 커서 보류; 실사용 단계로
  넘어갈 때 재검토.
