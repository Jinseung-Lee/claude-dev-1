# User identity

## Decisions

- 사용자는 이메일(아이디)과 비밀번호로 가입하고 로그인한다. 가입은
  Supabase Auth로 처리하며, 확인 메일 없이 즉시 완료된다.

## Boundaries

- 구글·카카오 소셜 로그인은 이 결정의 범위 밖이다. 필요해지면 이메일 가입
  방식에 추가하는 형태로 별도 검토한다.
- 비밀번호 찾기(이메일 재설정)도 이번 범위 밖이다. 이 프로젝트에 연결된
  Supabase의 기본 이메일 발송은 프로젝트 팀 멤버로 등록된 주소로만
  발송되고 시간당 2통으로 제한되어(Supabase 기본 SMTP 문서 확인), 실제
  가입자에게는 재설정 메일도 가입 확인 메일도 가지 않는다. 같은 이유로
  가입 확인 절차도 요구하지 않는다.
- 이 방식은 `docs/specs/trip-weather/`에서 처음 만든 로그인·마이 여행 저장
  기능 전반에 적용된다. 기존에 이메일만으로 만들어졌던 계정·여행 데이터는
  새 방식으로 이어지지 않는다.

## Why

초기 스펙(`docs/specs/trip-weather/`)에서는 강의용 첫 단계로 비밀번호 없는
이메일 식별을 썼다. 이후 사용자가 정식 계정 시스템으로 전환하기로
결정했다. 타인의 이메일만 입력해 그 사람의 여행 목록을 볼 수 있었던 이전
방식의 보안 위험이 이 결정으로 해소된다.

구글·카카오 로그인은 각각 별도 개발자 콘솔에서 앱 등록과 키 발급이
필요해, 이번 전환 범위에서는 이메일 가입만 먼저 다루기로 사용자와
합의했다. 비밀번호 찾기는 원래 계획에 있었지만, 커스텀 SMTP 연동 없이는
실제로 동작하지 않는다는 사실을 확인하고 나서, 새 서비스 가입까지 이번
범위에 넣는 대신 빼기로 사용자와 합의했다.

## Reconsider when

- 구글·카카오 같은 소셜 로그인이 필요해지는 시점: 이메일 가입 방식 위에
  추가하는 형태로 검토한다.
- 커스텀 SMTP(Resend·SendGrid 등)를 연동하기로 결정하는 시점: 비밀번호
  찾기와 가입 확인 메일을 다시 도입할 수 있다.

## Still-rejected alternatives

- 비밀번호 없는 이메일 식별 — 첫 스펙에서 쓰던 방식. 타인의 이메일만
  알면 목록을 볼 수 있는 보안 위험이 있어 정식 인증으로 전환하며
  폐기했다.
- 구글·카카오 소셜 로그인 — 개발자 콘솔 등록·키 발급 부담으로 이번
  범위에서 보류; 필요해지면 재검토.
- 비밀번호 찾기(이메일 재설정) — Supabase 기본 이메일 발송이 팀 멤버
  전용·시간당 2통 제한이라 실사용자에게 동작하지 않음을 확인하고 보류;
  커스텀 SMTP 연동을 결정하면 재검토.
